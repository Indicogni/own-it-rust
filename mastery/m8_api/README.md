# M8 · Library design, semver and stewardship

[All chapters](../../README.md) · [Concepts](CONCEPTS.md) · [Hints](HINTS.md) · [Notes](NOTES.md)

Chapters 1 to 24 taught you to write Rust that works. This module is about Rust that other people build on: a library with users you will never meet, who expect their code to compile after your next release. You learn to read a public interface as a set of promises, to say exactly which changes break one, to design a first version that leaves room for the later ones, and to ship a release that keeps an existing user working.

## Who it is for

You have finished chapters [1](../../exercises/chapter01/README.md) to [24](../../exercises/chapter24/README.md), or you write Rust at that level. You may never have published a crate; the module assumes only that you have used other people's.

## What is in the package

```text
m8_api/
├── CONCEPTS.md          the teaching text: read a section, then do its lesson
├── src/lNN_*.rs         the lessons: header, contract, tests, predictions
├── src/c01_code_review.rs   a library to review and rewrite
├── src/support.rs       the test tools; you do not edit this file
└── fixtures/            small libraries and the programs that use them
    ├── l01/ l02/        published libraries at 1.0.0, and programs written for them
    ├── l03/ l04/ c01/   cases: programs that are compiled against your lesson file
    ├── l05/swatch/      a package whose features you redesign, and four programs that use it
    ├── l06/slugger/     a package without documentation
    ├── l07/oldtimer/    a package that promises an old compiler
    └── l08/pacer/       the capstone: a library at 1.0.0, and two users
```

A library is judged from outside. So most checks in this module are not ordinary unit tests: they are programs that are compiled against a library the way a user would compile them, with `rustc` or with a second `cargo`. A program that must *not* compile is a check too. When such a check fails, the message tells you which program it was, what was expected, and why.

Lessons 01 to 03 give you signatures. From lesson 04 on the contract is prose and the design is yours; the tests name only the items that the contract names.

## Setup

This is a standalone Cargo package with its own `Cargo.lock` and no dependencies. Rust 1.99.0 is pinned in `rust-toolchain.toml`, identical to the one in the repository root. Run the commands from the repository root:

```sh
cargo test --manifest-path mastery/m8_api/Cargo.toml --locked --no-run
cargo test --manifest-path mastery/m8_api/Cargo.toml --locked --release --no-run
```

The starter compiles. Most tests fail at `todo!()`, at `guess()`, or because a library does not behave as the contract says yet. That is the starting state. A few tests pass from the start: they describe what your changes must keep.

Everything works offline. The tests start `rustc`, `rustdoc`, `cargo` and (in lesson 07) `cargo clippy`, all from the pinned toolchain. Their build output goes into this package's own target directory. The nested `cargo` runs write a `Cargo.lock` next to some fixture manifests; this package's `.gitignore` lists those files.

## Work through the module

1. **Read** the lesson's section in [CONCEPTS.md](CONCEPTS.md), then the header of the lesson file: what to predict, what to do, what to explain.
2. **Predict.** Answer the predictions first: replace each `guess()` with a value. Outcomes are written like in the drills: `"ok"`, `"panic"`, `"error"`, or an error code such as `"E0308"`. Some answers (a version number, a class of change) are checked by a digest, so they cannot be read from the test.
3. **Do the work.** In lessons 01 to 04 and 07 it is in the lesson file. In lessons 02, 05, 06, 07 and 08 it is also, or only, in `fixtures/`; the lesson header says where.
4. **Read the failing case.** When a check fails, open the program it names. The programs under `fixtures/*/cases/` and `fixtures/*/apps/` are the precise contract.
5. **Run clippy** and resolve the warnings in your code.
6. **Explain.** Write the EXPLAIN answer in [NOTES.md](NOTES.md), then compare with *Check your explanation* in [HINTS.md](HINTS.md).

## Mastery check

You have mastered this module when you can do these without looking anything up:

1. A manifest says `dep = "0.4.1"`. State which versions Cargo may choose, and the smallest correct next version of `dep` after (a) a bug fix, (b) a new function, (c) a removed function.
2. Given a diff of a public interface, sort each change into major, minor or possibly-breaking, and for each major one write a small program that the change breaks.
3. Explain how a change to a private field can break a user, and what you put into your test suite so that it cannot happen unnoticed.
4. Name the four tools for future-proofing, what each one takes away from the user, and one type for which you would deliberately use none of them.
5. Design an error type for a small parser so that callers can branch on the failure, a reporter can print the chain without repetition, and you can add a failure in a minor release.
6. Explain feature unification with a two-program example, and say why a feature must not change the type of an existing item.
7. Write documentation for a fallible function: a first sentence, `# Errors`, and an example with `?` that would fail if the documented edge case were implemented wrongly.
8. Retire a badly named function over two releases, and say which of your users can still be broken by the first of them.
9. Say what `rust-version` promises, two ways to check the promise, and what only one of them can see.
10. Redo the capstone after a break without looking at your first solution. Then decide what a 2.0.0 of `pacer` should remove, and write its changelog.

Model answers are at the end of [HINTS.md](HINTS.md).

## Where the solutions are

Model solutions are in [solutions/mastery/m8_api/](../../solutions/mastery/m8_api/), which mirrors this directory: `src/` has every lesson file with its predictions filled in, and `fixtures/` has the files that a lesson asks you to change (the witness programs of lesson 02, `swatch`, `slugger`, `oldtimer`, and `pacer` with its changelog). [solutions/drills/m8/](../../solutions/drills/m8/) has each drill repaired and the expected outcome of every drill in `expected.tsv`.

Use a solution after an honest attempt and after the hints. From lesson 04 on, your design may differ from the model and still be right: the cases decide. When it differs, note in NOTES.md what differs and what each choice costs a user.
